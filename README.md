<p align="center"><strong>CTM: Chovy！AI你写写代码给我写的啊！</strong></p>

<p align="center"><em>先骂。骂完让 AI 把好的写法和踩过的坑都记下来。下次少骂两句，最好一句都不用骂。</em></p>

<h2 align="center">用 Skill 和 few-shot 代码片段，一点点补齐仓库的编码规范，教 AI 用正确的姿势拉屎。</h2>

<p align="center"><a href="README_EN.md">English</a></p>

---

仓库没一套统一的编码规范。远古屎坑换了好几代人接手，AI 随便翻个文件照着写，同一个功能都能写出三种风格。

一个需求写下来，代码缠成一团。Review 不知道从哪儿下手，翻着翻着，又跟 AI 吵了一下午。

**活还没拿到，自己先成了受气包。**

我也试过往 `README.md` 里写规范，再在 `AGENTS.md` 里补一句「别乱改，先看 README」。每踩一个坑就补一条，补着补着，连 `README.md` 都开始拉屎了。

CTM！骂都骂了，把这次改对的写法、原来的反例，还有为什么要改，都留下来。

---

## AI 的几种拉屎方式

1. **便秘。** 函数光秃秃的，只有代码。调用前要满足什么条件，遇到边界情况会怎样，全靠 Review 的人猜。
2. **窜稀。** 代码明明一眼能看懂，AI 还要逐行解释。一千行里八百行都是注释，找代码得先扒拉半天。
3. **喷射。** 本来在一个函数里就能说清楚的几行代码，偏要拆得到处都是。Review 一个返回值，得在 N 个函数之间来回跳。
4. **兜不住了，先拉为敬。** 功能倒是写完了，耗时和复杂度一概没管。Review 时翻开代码，才发现写了一堆随时爆炸的sql。
5. ……

## 拉屎了怎么办

先把眼前的屎擦干净。改完用 `$ctm` / `/ctm` 把这次评审里的正反例、适用条件和判断理由记成候选。确认后再入库，下次改同类代码前就能直接查到。

**不是不拉，是缓拉，慢拉，有节奏地拉，正确地拉。**

## SKILL理念

每次骂完AI后，让AI复盘，记录你骂了什么，为什么骂，骂完之后改了什么。

**骂完就记 → 审完入库 → 下次写前先读 → 读完再写 → 写完继续 Review，踩坑了接着骂。**

团队里的每个人都可以按自己的判断，把评审中纠正的写法记成个人候选。收尾时挑出值得复用的例子，确认后放进个人库。需要全团队一起用的例子，再明确收进团队库。

### code-few-shot-manage

评审里刚说清楚哪段代码有问题、该怎么改，就用 [`code-few-shot-manage`](skills/code-few-shot-manage/SKILL.md) 把它记下来。它会保存正反例的代码片段、适用条件、判断理由和来源。正例和反例各有独立的候选编号，方便之后分别决定去留。

```text
项目根目录/
├── .code-few-shot-personal/
│   ├── candidates.md    # 待审的个人候选
│   ├── index.md         # 已入库的个人样例索引
│   └── few-shots/       # 按场景存放的正式样例
└── .code-few-shot/
    ├── index.md         # 团队样例索引
    └── few-shots/       # 团队共享的正式样例
```

复盘时默认先存个人候选。明确要求直接保存时，默认写入个人库的正式样例并更新索引。
要写团队库，明确指定团队库并确认要存的样例。
Git 项目里的个人库应保持未跟踪，并在根目录的 `.gitignore` 中加入 `/.code-few-shot-personal/`。

### code-few-shot-read

要实现新功能、修 Bug 或改现有代码时，先用 [`code-few-shot-read`](skills/code-few-shot-read/SKILL.md) 按场景查已入库的样例。每个场景先查个人库，个人库没匹配到再查团队库。两边都没找到适用的例子，就参考项目约定和附近的代码。待审候选入库后，才会进入这一步的检索范围。

### code-few-shot-check

收尾时用 [`code-few-shot-check`](skills/code-few-shot-check/SKILL.md)。可以只审个人候选，也可以按指定范围审查正式样例库。

- **审候选。** 看候选和正式样例有没有重复或冲突，再按编号选择入库、删除或暂留。入库时先验证正式样例和索引，再移除对应候选。
- **审正式库。** 检查冲突、可合并的样例、团队库对个人样例的覆盖，以及索引问题。它会给出带编号的修改预览，确认后处理选中的条目。

### ctm

**气到不知道该怎么办了？交给 CTM！边骂边 CTM，它会告诉你现在该干什么！**

手动调用 [`ctm`](skills/ctm/SKILL.md)，比如发送 `$ctm` 或 `/ctm`。它先看你这次有没有明确指定动作，再看最近的对话走到哪一步。

- **马上要写代码。** 先走 `code-few-shot-read`，把相关场景的样例翻出来。
- **刚骂完，已经说清楚哪段写错了、为什么。** 走 `code-few-shot-manage`，把这次的教训记下来。
- **这轮干完了，或者你明确要审候选。** 走 `code-few-shot-check`，按你指定的范围做收尾。

光凭上下文还定不下来时，它会问你现在想先做哪一步。选定后，它会按对应技能的流程执行。

## 真实使用

下面是一次 PHP 接口评审里的实际对话节选。项目内的路径和类名做了简化，保留了当时的决定和结果。

### 教他的时候顺便 CTM，让他记住

> **用户**　`$ctm` 一般来说我们更希望它是降序排列的。出现 `orderBy()` 时，明确写上排序方向，默认用降序。

AI 把候选列表改成 `->orderBy('id', 'desc')`。回归测试验证返回顺序为 `[29, 24, 21]`，15 项测试、141 个断言通过。

CTM 选了 `code-few-shot-manage`，整理出一组「查询排序」候选。正例是 `->orderBy('id', 'desc')`，反例是省略方向的 `->orderBy('id')`。这个项目约定默认降序，业务要求升序时明确写 `asc`。

### 干完了，回头看看哪些值得记

> **用户**　`$ctm` 回顾一下，看看都纠正了你哪些。

AI 从这轮评审里找出三项还没入库的候选。

| 候选 | 记下来的写法 |
| --- | --- |
| 查询排序 | `orderBy()` 显式写方向，项目默认 `desc`。 |
| PHPDoc 与可空类型 | 给 `first()` 的赋值补上 `@var InspectionDetail\|null`，让 IDE 看得出具体模型和可空性。 |
| 模型状态与文案 | 给字段的全部有效状态定义常量，用常量作为文案映射的键。查询按需引用其中的状态。 |

> **用户**　全部加入。

AI 将三组正反例写入个人库，更新索引并核对了 Git 忽略状态。新版审阅已记录的候选时，会按 `P-<UUID>` 展示，你可以分别决定入库、删除或暂留。

### 审一遍样例库，再决定哪些给团队用

> **用户**　`$ctm` 检查一下模板代码。

`code-few-shot-check` 读完了个人库的 **10 个场景、44 个样例**，其中 24 个正例、20 个反例。它先给报告，把决定留给用户。当时还没有团队库，也没有待审的候选文件。

| 编号 | AI 找到的问题 | 用户的决定 |
| --- | --- | --- |
| `C-P-01` | 事务测试的正例用了省略方向的 `orderBy('id')`，与排序样例冲突。 | 所有相关正例显式用 `desc`，测试的预期顺序也一起改。 |
| `C-P-02` | 角色预加载正例没有说明 `with()` 加载了什么、用来做什么。 | 给关联补上用途注释。 |
| `R-P-01` | 一组旧代码摘录的字段和当前实现对不上。 | 保留仍能说明规则的旧摘录，来源记评审日期和决定。 |

AI 按前两项修改了个人样例，并撤下第三项建议。用户随后明确要求「`$ctm` 检查并加入团队规范」，CTM 先核对个人库，再把已确认的**排序方向**和 **Eloquent 预加载注释**收进团队库。

### 后续再做一次独立 Review

> **用户**　起一个独立的 sub-agent，从中立角度检查代码逻辑、Bug 和可以优化的地方。

独立 Review 继续检查了当前实现。它发现两处可空类型标注已经补在工作区，暂存版本还没带上。它也指出 `detail.*` 会多返回一个关联字段，以及按日期逐次查询冲突可以改成一次批量查询。这里审的是代码本身，样例库里已经记下的规范仍可以在 Review 时拿来核对。
